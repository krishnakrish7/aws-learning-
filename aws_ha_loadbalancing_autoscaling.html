⚖️
Elastic Load Balancer (ELB)
Distributes traffic across targets. Three types — each for a different use case.
Traffic Distribution
ALB — Application LB ⭐
Layer 7 — HTTP/HTTPS
Routes based on URL path (/api → service A, /images → service B)
Routes based on hostname (api.example.com vs web.example.com)
Supports WebSocket and HTTP/2
Targets: EC2, ECS, Lambda, IP addresses
Has a static DNS name (not static IP)
Trigger: microservices • path-based routing • containers • HTTP
NLB — Network LB
Layer 4 — TCP/UDP/TLS
Handles millions of requests per second
Ultra-low latency — ~100ms vs ALB ~400ms
Has static IP address per AZ (or Elastic IP)
Supports TCP, UDP, TLS protocols
Used for gaming, IoT, financial trading
Trigger: static IP • extreme performance • TCP/UDP • gaming
GWLB — Gateway LB
Layer 3 — IP Packets
Routes traffic through third-party security appliances
Intrusion detection, firewalls, deep packet inspection
All traffic passes through security appliance first
Uses GENEVE protocol on port 6081
Trigger: firewall • intrusion detection • security appliance • inspect traffic
⚠️ Most Common ELB Trap — ALB vs NLB
Choose ALB when...
• HTTP/HTTPS traffic
• Need URL path routing
• Microservices / containers
• WebSocket support needed
Choose NLB when...
• Need static IP address
• TCP/UDP protocols
• Extreme low latency
• Millions of req/sec
Key difference to remember
ALB = smart routing (knows about URLs)
NLB = raw speed (doesn't care about content)
GWLB = security inspection (routes through appliances)

📈
Auto Scaling Groups (ASG)
Automatically scale EC2 instances in or out based on demand. Always paired with ELB.
Auto Scaling
⚙️ Core Configuration
▸
Minimum capacity — never go below this (e.g. min: 2)
▸
Desired capacity — target number right now (e.g. desired: 4)
▸
Maximum capacity — never exceed this (e.g. max: 10)
▸
Launch Template — defines what EC2 to launch (AMI, instance type, security groups)
▸
Health checks — replaces unhealthy instances automatically
🔑 Key Exam Facts
▸
Free to use — you pay for the EC2 instances, not ASG itself
▸
Spans multiple AZs — automatically balances instances across AZs
▸
Cooldown period — wait time after scaling before next action (default 300s)
▸
Lifecycle hooks — run scripts before instance goes in service or terminates
▸
Termination policy: terminates instance in AZ with most instances first
Scaling Policies — Know All 4
🎯
Target Tracking
Set a target metric. AWS manages scaling automatically.
"Keep CPU at 50%"
📊
Step Scaling
Different scaling actions for different alarm thresholds.
"CPU >70% add 2, CPU >90% add 5"
📅
Scheduled Scaling
Scale based on known time patterns.
"Every Monday 9am add 10 instances"
🔮
Predictive Scaling
ML analyses historical patterns, scales proactively.
"Forecast next week's load"
Most recommended → Target Tracking (simplest)
Known schedule → Scheduled Scaling
Fine-grained control → Step Scaling
Recurring patterns → Predictive Scaling
🔄
Disaster Recovery Strategies
4 strategies — cost vs recovery speed trade-off. Know them in order.
DR Strategies
← Cheapest · Slowest recovery
Most expensive · Fastest recovery →
1. Backup & Restore
RTO/RPO: Hours
Cost: 💲 Lowest
Backup data to S3. Restore from scratch when disaster hits. Cheapest but slowest.
2. Pilot Light
RTO/RPO: ~10 mins
Cost: 💲💲 Low
Core systems (DB) always running in AWS at minimal scale. Scale up quickly on disaster.
3. Warm Standby
RTO/RPO: ~Minutes
Cost: 💲💲💲 Medium
Full scaled-down version always running. Just scale it up to full production size on failover.
4. Multi-Site Active/Active
RTO/RPO: ~0 (real-time)
Cost: 💲💲💲💲 Highest
Full production running in multiple regions simultaneously. Instant failover. Most expensive.
RTO = Recovery Time Objective — how long to restore service  |  RPO = Recovery Point Objective — how much data you can afford to lose

🎯 Exam Scenario Quick-Fire
Scenario 1
"Route /api to one target group and /web to another"
→ ALB with path-based routing rules
Scenario 2
"App needs a static IP address for whitelisting by clients"
→ NLB (has static IP per AZ)
Scenario 3
"All traffic must pass through a firewall appliance before reaching EC2"
→ Gateway Load Balancer
Scenario 4
"Scale EC2 fleet to keep average CPU usage at 60%"
→ ASG with Target Tracking scaling policy
Scenario 5
"Add 10 instances every Friday at 5pm for weekend traffic"
→ ASG with Scheduled Scaling
Scenario 6
"Cheapest DR — can tolerate hours of downtime"
→ Backup & Restore strategy
Scenario 7
"Near-zero RTO/RPO — business critical, cost not a concern"
→ Multi-Site Active/Active
Scenario 8
"One AZ goes down — users should not notice any interruption"
→ ELB + ASG across multiple AZs
Scenario 9
"App has recurring traffic spike every Monday morning"
→ ASG with Predictive Scaling
