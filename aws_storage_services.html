EBS — Elastic Block Store
Network-attached drive for a single EC2 instance. Lives in one AZ.
Block Storage
gp2
General Purpose SSD (old)
Baseline 3 IOPS/GB, bursts to 3,000
Legacy — prefer gp3
gp3 ⭐
General Purpose SSD (new)
Baseline 3,000 IOPS, cheaper than gp2
Best for most workloads
io1/io2
Provisioned IOPS SSD
Up to 64,000 IOPS. High-perf databases
Only type = Multi-Attach
st1
Throughput Optimised HDD
Big data, Kafka, log processing
Not bootable
sc1
Cold HDD
Infrequent access, lowest cost HDD
Not bootable
📍 One AZ only
🔌 One EC2 at a time (except io Multi-Attach)
📸 Snapshots stored in S3
🔄 Move AZ via snapshot → new volume
📦 Incremental snapshots
📂
EFS — Elastic File System
Shared NFS file system. Multiple EC2s access simultaneously. Auto-scales. Linux only.
Shared File System
🐧 Linux / NFS only
♾️ Auto-scales (no provisioning)
🌍 Multi-AZ access
💰 More expensive than EBS per GB
👥 Hundreds of EC2s simultaneously
📦 Storage Classes
EFS Standard
Frequently accessed files. Full performance.
EFS Infrequent Access (IA)
Rarely accessed. Much cheaper. Enable via lifecycle policy.
🎯 Exam trigger words: "shared", "multiple EC2", "Auto Scaling Group needs same files", "Linux NFS"
🗃️
FSx — Managed Specialised File Systems
When EFS isn't enough. Windows (SMB) or extreme HPC performance.
Specialised FS
🪟 FSx for Windows File Server
Uses SMB protocol (Windows native)
Integrates with Active Directory
Supports NTFS, DFS namespaces
Multi-AZ deployment available
Trigger: Windows • Active Directory • SMB • NTFS
⚡ FSx for Lustre
Sub-millisecond latency, 100s GB/s throughput
Integrates natively with S3 as backend
Ideal for ML training, genomics, video processing
POSIX-compliant, Linux compatible
Trigger: HPC • ML • extreme performance • Lustre

Lazy Loading (Cache-Aside)
Check cache → miss → query DB → store in cache → return. Risk: stale data.
Write-Through
Write to DB + cache simultaneously. Cache always fresh. Risk: write latency.
⚡ DAX (DynamoDB only)
Purpose-built for DynamoDB. No code changes needed. ms → μs reads.

🎯 Exam Scenario Quick-Fire
Scenario 1
"Oracle DB on EC2 requires 50,000 IOPS"
→ EBS io1 or io2
Scenario 2
"10 Linux EC2s in an ASG need the same shared config files"
→ EFS
Scenario 3
"Windows app needs shared SMB file share with Active Directory"
→ FSx for Windows
Scenario 4
"RDS MySQL overwhelmed with reads — reduce DB load"
→ ElastiCache (Redis)
Scenario 5
"DynamoDB needs microsecond response times"
→ DAX
Scenario 6
"ML training jobs need extreme throughput shared storage"
→ FSx for Lustre
Scenario 7
"Move EC2 instance to a different AZ"
→ EBS Snapshot → new volume in target AZ
Scenario 8
"Session storage that must survive cache node failure"
→ ElastiCache Redis (has persistence)
Scenario 9
"Most cost-effective general purpose SSD for a web server"
→ EBS gp3
